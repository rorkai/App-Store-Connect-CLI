# Version Management Commands

> Manage App Store versions, builds, and releases

## Overview

Version management commands allow you to create, update, delete, and manage App Store versions.

## Commands

### `asc versions list`

List app store versions for an app.

<ParamField path="--app" type="string" required>
  App Store Connect app ID (or `ASC_APP_ID` env variable)
</ParamField>

<ParamField path="--version" type="string">
  Filter by version string (comma-separated)
</ParamField>

<ParamField path="--platform" type="string">
  Filter by platform: `IOS`, `MAC_OS`, `TV_OS`, `VISION_OS` (comma-separated)
</ParamField>

<ParamField path="--state" type="string">
  Filter by state: `PREPARE_FOR_SUBMISSION`, `WAITING_FOR_REVIEW`, `IN_REVIEW`, `PENDING_DEVELOPER_RELEASE`, `READY_FOR_SALE` (comma-separated)
</ParamField>

<ParamField path="--limit" type="integer">
  Maximum results per page (1-200)
</ParamField>

<ParamField path="--next" type="string">
  Next page URL from a previous response
</ParamField>

<ParamField path="--paginate" type="boolean" default="false">
  Automatically fetch all pages (aggregate results)
</ParamField>

**Examples:**

```bash  theme={null}
asc versions list --app "123456789"
asc versions list --app "123456789" --version "1.0.0"
asc versions list --app "123456789" --platform IOS --state READY_FOR_REVIEW
asc versions list --app "123456789" --paginate
```

**Response:**

```json  theme={null}
{
  "data": [
    {
      "id": "VERSION_ID",
      "type": "appStoreVersions",
      "attributes": {
        "versionString": "1.0.0",
        "platform": "IOS",
        "appStoreState": "READY_FOR_SALE",
        "createdDate": "2024-01-15T10:30:00.000+0000"
      }
    }
  ]
}
```

### `asc versions view`

View details for an app store version.

In 1.0, the deprecated `asc versions get` alias was removed. Use
`asc versions view` as the canonical command.

Provide either `--version-id`, or the `--app` and `--version`
selectors. `--platform` defaults to `IOS` for selector-based lookup.
Selector lookup first resolves the version ID, then fetches its details. Use
`--version-id` to retain the single-request path for automation. Conflicting or
incomplete selectors, and unsupported platform values, exit with a usage error
before authentication or API requests.

<ParamField path="--version-id" type="string">
  App Store version ID. Cannot be combined with the alternate selectors.
</ParamField>

<ParamField path="--app" type="string">
  App Store Connect app ID (or `ASC_APP_ID`)
</ParamField>

<ParamField path="--version" type="string">
  Version string used with `--app`
</ParamField>

<ParamField path="--platform" type="string" default="IOS">
  Platform used with `--app` and `--version`: `IOS`, `MAC_OS`, `TV_OS`, or `VISION_OS`
</ParamField>

<ParamField path="--include-build" type="boolean" default="false">
  Include attached build information
</ParamField>

<ParamField path="--include-submission" type="boolean" default="false">
  Include submission information
</ParamField>

<ParamField path="--include" type="string">
  Include related resources (comma-separated): `ageRatingDeclaration`, `app`, `appStoreVersionLocalizations`, `build`, `appStoreVersionPhasedRelease`, `gameCenterAppVersion`, `routingAppCoverage`, `appStoreReviewDetail`, `appStoreVersionSubmission`, `appClipDefaultExperience`, `appStoreVersionExperiments`, `appStoreVersionExperimentsV2`, `alternativeDistributionPackage`
</ParamField>

**Examples:**

```bash  theme={null}
asc versions view --version-id "VERSION_ID"
asc versions view --app "123456789" --version "1.2.3"
asc versions view --app "123456789" --version "1.2.3" --platform MAC_OS
asc versions view --version-id "VERSION_ID" --include build
asc versions view --version-id "VERSION_ID" --include-build --include-submission
asc versions view --version-id "VERSION_ID" --include "ageRatingDeclaration,appStoreReviewDetail"
```

**Response:**

View prints Apple's `appStoreVersions` envelope: every
attribute Apple returns (including `appStoreState`, `releaseType`,
`copyright`, `reviewType`, `usesIdfa`, and null values such as
`"earliestReleaseDate": null`), `relationships`, `included`, and `links`. Two
exceptions: an included `appStoreReviewDetails` demo account password is
redacted unless you pass `--include-sensitive`, and `ageRatingDeclaration` is
fetched with a second request and added to `included`.

In 6.0.0, the deprecated reduced summary is replaced by this envelope for every
view. Read version fields from `data.attributes`; the state is
`data.attributes.appVersionState` (or `data.attributes.appStoreState`).
`--include-build` and `--include-submission` remain supported aliases for
`--include build` and `--include appStoreVersionSubmission`.

```json  theme={null}
{
  "data": {
    "type": "appStoreVersions",
    "id": "VERSION_ID",
    "attributes": {
      "versionString": "1.0.0",
      "platform": "IOS",
      "appStoreState": "READY_FOR_SALE"
    }
  }
}
```

### `asc versions create`

Create a new app store version.

<ParamField path="--app" type="string" required>
  App Store Connect app ID (or `ASC_APP_ID` env variable)
</ParamField>

<ParamField path="--version" type="string" required>
  Version string (e.g., 1.0.0)
</ParamField>

<ParamField path="--platform" type="string" default="IOS">
  Platform: `IOS`, `MAC_OS`, `TV_OS`, `VISION_OS`
</ParamField>

<ParamField path="--copyright" type="string">
  Copyright text (e.g., '2026 My Company')
</ParamField>

<ParamField path="--release-type" type="string">
  Release type: `MANUAL`, `AFTER_APPROVAL`, `SCHEDULED`
</ParamField>

<ParamField path="--earliest-release-date" type="string">
  Earliest release date (ISO 8601, e.g., 2026-02-01T08:00:00+00:00)
</ParamField>

<ParamField path="--review-type" type="string">
  Review type: `APP_STORE`, `NOTARIZATION`
</ParamField>

<ParamField path="--build-id" type="string">
  Build ID to attach in the create request. With `--if-exists update`, attaches it to an existing version instead. Cannot be used with `--if-exists skip`.
</ParamField>

**Examples:**

```bash  theme={null}
asc versions create --app "123456789" --version "2.0.0"
asc versions create --app "123456789" --version "2.0.0" --platform IOS
asc versions create --app "123456789" --version "2.0.0" --copyright "2026 My Company" --release-type MANUAL
asc versions create --app "123456789" --version "2.0.0" --release-type SCHEDULED --earliest-release-date "2026-02-01T08:00:00+00:00"
asc versions create --app "123456789" --version "2.0.0" --review-type NOTARIZATION
asc versions create --app "123456789" --version "2.0.0" --build-id "BUILD_ID"
```

**Response:**

```json  theme={null}
{
  "id": "NEW_VERSION_ID",
  "versionString": "2.0.0",
  "platform": "IOS",
  "state": "PREPARE_FOR_SUBMISSION"
}
```

### `asc versions update`

Update an app store version.

<ParamField path="--version-id" type="string" required>
  App Store version ID
</ParamField>

<ParamField path="--copyright" type="string">
  Copyright text (e.g., '2026 My Company')
</ParamField>

<ParamField path="--release-type" type="string">
  Release type: `MANUAL`, `AFTER_APPROVAL`, `SCHEDULED`
</ParamField>

<ParamField path="--review-type" type="string">
  Review type: `APP_STORE`, `NOTARIZATION`
</ParamField>

<ParamField path="--earliest-release-date" type="string">
  Earliest release date (ISO 8601, e.g., 2026-02-01T08:00:00+00:00)
</ParamField>

<ParamField path="--version" type="string">
  Version string (e.g., 1.0.1)
</ParamField>

<ParamField path="--downloadable" type="boolean">
  Download availability for this version on older operating systems and devices (`true` or `false`). This is the public API surface behind App Store Connect's Last-Compatible Version Settings screen. The flag is tri-state: leaving it unset sends no `downloadable` attribute, so an unrelated update never changes download availability.
</ParamField>

<ParamField path="--confirm" type="boolean">
  Required with `--downloadable false`, because making a previously released version unavailable for download is not reversible from every state. It is rejected as a usage error in any other combination rather than silently ignored, including an explicit `--confirm=false`.
</ParamField>

**Examples:**

```bash  theme={null}
asc versions update --version-id "VERSION_ID" --copyright "2026 My Company"
asc versions update --version-id "VERSION_ID" --release-type MANUAL
asc versions update --version-id "VERSION_ID" --review-type NOTARIZATION
asc versions update --version-id "VERSION_ID" --release-type SCHEDULED --earliest-release-date "2026-02-01T08:00:00+00:00"
asc versions update --version-id "VERSION_ID" --version "1.0.1"
asc versions update --version-id "VERSION_ID" --downloadable true
asc versions update --version-id "VERSION_ID" --downloadable false --confirm
```

Read the current value with `asc versions list --app "APP_ID" --paginate --output json` or `asc versions view --version-id "VERSION_ID" --output json`. `--paginate` matters here because the oldest versions, the ones this setting usually targets, fall past the first page. Apple omits `downloadable` for versions that never carried the setting, so an absent key means Apple did not report the attribute.

**Response:**

```json  theme={null}
{
  "id": "VERSION_ID",
  "versionString": "1.0.1",
  "platform": "IOS",
  "state": "PREPARE_FOR_SUBMISSION"
}
```

### `asc versions attach-build`

Attach a build to an app store version.

Select the version with `--version-id`, or with `--app` and `--version`. Select
the build with `--build-id`, `--build-number`, or `--latest`. `--build-number`
and `--latest` only match builds of the version's app, version string, and
platform, and the selected build must be `VALID` unless `--wait` waits for
processing first. Internal-only builds cannot be used for App Store distribution;
`--latest` selects the newest App Store eligible build in the train.

<ParamField path="--version-id" type="string">
  App Store version ID
</ParamField>

<ParamField path="--app" type="string">
  App Store Connect app ID, bundle ID, or exact app name. Required with `--version`, `--platform`, `--build-number`, or `--latest`
</ParamField>

<ParamField path="--version" type="string">
  App Store version string, resolved with `--app` and `--platform`
</ParamField>

<ParamField path="--platform" type="string" default="IOS">
  Platform: `IOS`, `MAC_OS`, `TV_OS`, `VISION_OS`
</ParamField>

<ParamField path="--build-id" type="string">
  Build ID to attach
</ParamField>

<ParamField path="--build-number" type="string">
  Build number (CFBundleVersion) to attach from the version's train
</ParamField>

<ParamField path="--latest" type="boolean">
  Attach the most recently uploaded App Store eligible build of the version's train. Right after an upload, prefer `--build-number`
</ParamField>

<ParamField path="--wait" type="boolean">
  Wait for the selected build to finish processing before attaching. Use `--timeout` and `--poll-interval` to tune it
</ParamField>

**Examples:**

```bash  theme={null}
asc versions attach-build --version-id "VERSION_ID" --build-id "BUILD_ID"
asc versions attach-build --app "123456789" --version "1.2.0" --build-number "45"
asc versions attach-build --app "123456789" --version "1.2.0" --build-number "46" --wait --timeout 30m
```

**Response:**

```json  theme={null}
{
  "versionId": "VERSION_ID",
  "buildId": "BUILD_ID",
  "attached": true
}
```

### `asc versions release`

Release an approved version in the Pending Developer Release state.

The request is sent once. If Apple answers with a server error or the request times out, `asc` reads the version back. When the version has left Pending Developer Release, the command succeeds with `"reconciled": true`, the current `versionState`, an empty `releaseRequestId`, and a note on stderr. Otherwise it reports the original error.

<ParamField path="--version-id" type="string" required>
  App Store version ID
</ParamField>

<ParamField path="--confirm" type="boolean" required>
  Confirm release request (required)
</ParamField>

**Examples:**

```bash  theme={null}
asc versions release --version-id "VERSION_ID" --confirm
```

**Response:**

```json  theme={null}
{
  "releaseRequestId": "RELEASE_REQUEST_ID",
  "versionId": "VERSION_ID"
}
```

### `asc versions rating-reset`

Schedule, inspect, or cancel the overview-rating reset for
an App Store version. Apple doesn't include this web-session endpoint in its
published OpenAPI specification, so the resource may change without notice.

The reset affects every country or region for the selected platform when the
version is released. Written reviews remain visible. After release, the
previous overview rating can't be restored.

These commands use an authenticated Apple Account web session. Run `asc web
auth login` first when no valid cached session is available. Use `--apple-id`
to select a specific cached account and `--provider-id` or
`--public-provider-id` to select its App Store Connect provider.

View the current request:

```bash  theme={null}
asc versions rating-reset view --version-id "VERSION_ID"
```

Schedule a reset:

```bash  theme={null}
asc versions rating-reset create --version-id "VERSION_ID" --confirm
```

Cancel it before release:

```bash  theme={null}
asc versions rating-reset delete --id "RESET_REQUEST_ID" --confirm
```

The create command returns:

```json  theme={null}
{
  "ratingResetRequestId": "RESET_REQUEST_ID",
  "versionId": "VERSION_ID",
  "scheduled": true
}
```

The delete command returns:

```json  theme={null}
{
  "ratingResetRequestId": "RESET_REQUEST_ID",
  "cancelled": true
}
```

## Common Usage Patterns

### Create a new version and attach a build

```bash  theme={null}
asc versions create --app "123456789" --version "2.0.0" --platform IOS
asc versions attach-build --app "123456789" --version "2.0.0" --build-number "45"
```

### List versions in a specific state

```bash  theme={null}
asc versions list --app "123456789" --state WAITING_FOR_REVIEW,IN_REVIEW
```

### Find the live version

App Store Connect reports a live version as `appVersionState` `READY_FOR_DISTRIBUTION`, the deprecated `appStoreState` `READY_FOR_SALE`, or both, and one `--state` filter cannot match both. Replaced versions can still report `READY_FOR_SALE`, so list that state with `--paginate` rather than `--latest`, skip results whose `appVersionState` is present and is not `READY_FOR_DISTRIBUTION`, and keep the newest version left on each platform across both lists.

```bash  theme={null}
asc versions list --app "123456789" --state READY_FOR_DISTRIBUTION --latest
asc versions list --app "123456789" --state READY_FOR_SALE --paginate
```

### Update version release type

```bash  theme={null}
asc versions update --version-id "VERSION_ID" --release-type SCHEDULED --earliest-release-date "2026-03-01T08:00:00+00:00"
```

### Release a pending version

```bash  theme={null}
asc versions release --version-id "VERSION_ID" --confirm
```

## Version States

* `PREPARE_FOR_SUBMISSION` - Version is being prepared
* `WAITING_FOR_REVIEW` - Version is waiting for Apple review
* `IN_REVIEW` - Version is currently under review
* `PENDING_CONTRACT` - Pending contract approval
* `WAITING_FOR_EXPORT_COMPLIANCE` - Waiting for export compliance
* `PENDING_DEVELOPER_RELEASE` - Approved and waiting for developer to release
* `PROCESSING_FOR_APP_STORE` - Processing for release
* `PENDING_APPLE_RELEASE` - Pending Apple release
* `READY_FOR_DISTRIBUTION` - Live on the App Store (`appVersionState`)
* `READY_FOR_SALE` - Live on the App Store (deprecated `appStoreState`; replaced versions can still report it)
* `REMOVED_FROM_SALE` - Removed from sale
* `DEVELOPER_REJECTED` - Rejected by developer
* `REJECTED` - Rejected by Apple
* `METADATA_REJECTED` - Metadata rejected
* `INVALID_BINARY` - Binary is invalid
