# Workflow Automation

> Automate complex App Store Connect workflows with multi-step sequences

Define and execute multi-step automation workflows that combine multiple CLI commands and shell scripts.

## Overview

Workflows allow you to:

* Chain multiple `asc` commands together
* Run shell scripts and commands
* Pass data between steps
* Handle errors with hooks
* Execute conditional steps
* Compose reusable sub-workflows

<Warning>
  Workflows intentionally execute arbitrary shell commands. Only run workflow files you trust, especially when using `--file`. Treat `.asc/workflow.json` like code: review it before running.
</Warning>

## Quick Start

### Create a Workflow File

Create `.asc/workflow.json` in your project:

```json  theme={null}
{
  "env": {
    "APP_ID": "123456789",
    "VERSION": "1.0.0"
  },
  "workflows": {
    "beta": {
      "description": "Distribute latest build to beta testers",
      "steps": [
        {
          "name": "get_latest_build",
          "run": "asc builds list --app $APP_ID --sort -uploadedDate --limit 1 --output json"
        },
        {
          "name": "add_to_group",
          "run": "asc builds add-groups --build-id $BUILD_ID --group $GROUP_ID"
        }
      ]
    }
  }
}
```

### Run a Workflow

```bash  theme={null}
asc workflow run beta BUILD_ID:abc123 GROUP_ID:def456
```

### List Available Workflows

```bash  theme={null}
asc workflow list
```

### Validate Workflow File

```bash  theme={null}
asc workflow validate
```

## Workflow Structure

### Basic Workflow

```json  theme={null}
{
  "env": {
    "GLOBAL_VAR": "value"
  },
  "before_all": "echo Starting workflows",
  "after_all": "echo All workflows complete",
  "error": "echo Error occurred",
  "workflows": {
    "workflow_name": {
      "description": "What this workflow does",
      "env": {
        "WORKFLOW_VAR": "value"
      },
      "steps": [
        {
          "name": "step_1",
          "run": "command to execute"
        }
      ]
    }
  }
}
```

### Environment Variables

**Global Environment** (`env` at root):

* Available to all workflows
* Merged with system environment

**Workflow Environment** (`env` in workflow):

* Scoped to specific workflow
* Overrides global variables

**Runtime Parameters**:

* Passed via command line: `KEY:VALUE`
* Override workflow environment

Precedence for steps in the workflow you invoked (highest to lowest):

1. Runtime parameters
2. Workflow `env`
3. Global `env`
4. System environment

Precedence for steps inside a called sub-workflow (highest to lowest):

1. The calling step's `with`
2. Runtime parameters
3. Calling workflow's `env`
4. Global `env`
5. Called workflow's own `env`
6. System environment

A sub-workflow's own `env` is the lowest-priority map in its own scope, so it
provides defaults the caller overrides. The calling step's `with` is the only
source that outranks runtime parameters: a key hardcoded there cannot be
overridden with `KEY:VALUE`. `with` values are literal — only
`${steps.NAME.OUTPUT}` references are interpolated.

### Hooks

**before\_all**: Runs before any workflow

```json  theme={null}
"before_all": "asc auth status"
```

**after\_all**: Runs after successful workflow

```json  theme={null}
"after_all": "echo Success! && notify-send 'Workflow Complete'"
```

**error**: Runs when workflow fails

```json  theme={null}
"error": "echo Failed! && notify-send 'Workflow Failed'"
```

## Step Types

### Command Steps

Execute shell commands:

```json  theme={null}
{
  "name": "list_builds",
  "run": "asc builds list --app $APP_ID --limit 5"
}
```

### Conditional Steps

`if` names a variable and runs the step only when that variable holds a truthy
value: `1`, `true`, `yes`, `y`, or `on` (case-insensitive, surrounding
whitespace ignored):

```json  theme={null}
{
  "name": "optional_step",
  "if": "INSPECT_BUILD",
  "run": "asc builds info --build-id $BUILD_ID"
}
```

Run it with `asc workflow run beta INSPECT_BUILD:true`. The variable is resolved
from the workflow environment first (runtime parameters, `with`, workflow `env`,
global `env`) and then from the process environment.

Every other value is falsy, including an unset variable, an empty string, and
any other non-empty value. `"if": "BUILD_ID"` with `BUILD_ID:abc123`, or
`"if": "IPA_PATH"` with a path, always skips the step. Use `if` as a boolean
feature flag, never as a "was this ID supplied?" check.

<Warning>
  A skipped step is not a failure: the run still reports `"status": "ok"` and
  exits `0`, with `"status": "skipped"` on that entry in `steps[]`. A mutating
  step gated on a non-boolean value never runs while CI stays green.
</Warning>

### Sub-Workflow Steps

Call another workflow:

```json  theme={null}
{
  "workflow": "preflight",
  "with": {
    "EXTRA_VAR": "value"
  }
}
```

The called workflow receives `EXTRA_VAR` in addition to its own environment.

## Passing Data Between Steps

Each step runs in its own shell, so a variable assigned inside one step is gone
by the next one. `BUILD_ID=$(...)` in step 2 is **not** visible to step 3.

To move a value forward, declare `outputs` on a step and reference them as
`${steps.<step_name>.<OUTPUT_NAME>}`. The step must print JSON on stdout, so
pass `--output json` to `asc` commands. Each output is a JSON path rooted at
`$.` and may only walk object keys (no array indexes):

```json  theme={null}
{
  "steps": [
    {
      "name": "resolve_build",
      "run": "asc builds info --app $APP_ID --latest --platform IOS --output json",
      "outputs": {
        "BUILD_ID": "$.data.id"
      }
    },
    {
      "name": "distribute",
      "run": "asc builds add-groups --build-id ${steps.resolve_build.BUILD_ID} --group \"$GROUP_NAME\""
    }
  ]
}
```

Interpolated values are shell-quoted, and numbers keep the exact form the
command emitted (a build number of `42` stays `42`). Declared outputs are also
persisted in the run-state file, so never map a secret into `outputs`.

## Complete Workflow Examples

### Beta Distribution Workflow

```json  theme={null}
{
  "env": {
    "APP_ID": "123456789"
  },
  "workflows": {
    "beta": {
      "description": "Distribute latest build to TestFlight beta group",
      "env": {
        "GROUP_NAME": "External Beta",
        "DISTRIBUTE": "false"
      },
      "steps": [
        {
          "name": "validate_auth",
          "run": "asc auth status"
        },
        {
          "name": "resolve_build",
          "run": "asc builds info --app $APP_ID --latest --platform IOS --output json",
          "outputs": {
            "BUILD_ID": "$.data.id"
          }
        },
        {
          "name": "add_build_to_group",
          "if": "DISTRIBUTE",
          "run": "asc builds add-groups --build-id ${steps.resolve_build.BUILD_ID} --group \"$GROUP_NAME\"",
          "retry": {
            "max_attempts": 6,
            "delay": "10s"
          },
          "timeout": "2m"
        },
        {
          "name": "notify_success",
          "if": "DISTRIBUTE",
          "run": "echo Build ${steps.resolve_build.BUILD_ID} distributed to $GROUP_NAME"
        }
      ]
    }
  }
}
```

Run with:

```bash  theme={null}
asc workflow run beta DISTRIBUTE:true
```

Leave `DISTRIBUTE` off to resolve the latest build without touching the group:

```bash  theme={null}
asc workflow run beta
```

### App Store Submission Workflow

```json  theme={null}
{
  "env": {
    "APP_ID": "123456789",
    "IPA_PATH": "./build/MyApp.ipa",
    "PLATFORM": "IOS",
    "SUBMIT": "false"
  },
  "before_all": "echo Starting submission workflow",
  "after_all": "echo Submission complete!",
  "error": "echo Submission failed - check logs",
  "workflows": {
    "release": {
      "description": "Publish latest build to the App Store",
      "steps": [
        {
          "name": "validate_metadata",
          "run": "asc localizations list --version $VERSION_ID --output json | jq -e '.data | length > 0'"
        },
        {
          "name": "ensure_ipa",
          "run": "test -f \"$IPA_PATH\""
        },
        {
          "name": "publish_release",
          "if": "SUBMIT",
          "run": "asc publish appstore --app $APP_ID --ipa $IPA_PATH --version $VERSION --submit --confirm"
        },
        {
          "name": "check_status",
          "run": "asc submit status --version-id $VERSION_ID"
        }
      ]
    }
  }
}
```

Run with:

```bash  theme={null}
asc workflow run release SUBMIT:true VERSION:1.0.0 VERSION_ID:abc123
```

`SUBMIT:true` is what makes `publish_release` execute. Gating it on `IPA_PATH`
instead would skip the submission on every run, because `./build/MyApp.ipa` is
not a truthy value. Presence of the file belongs in a real check such as the
`ensure_ipa` step above. Drop `SUBMIT:true` for a metadata-only dry pass:

```bash  theme={null}
asc workflow run release VERSION:1.0.0 VERSION_ID:abc123
```

### Complete Release Workflow

```json  theme={null}
{
  "env": {
    "APP_ID": "123456789",
    "PLATFORM": "IOS",
    "IPA_PATH": "./build/MyApp.ipa",
    "SUBMIT": "false"
  },
  "before_all": "git fetch --tags && git status",
  "after_all": "echo Release workflow complete!",
  "error": "echo ERROR: Release failed",
  "workflows": {
    "release": {
      "description": "Complete release: version creation, metadata, screenshots, submission",
      "steps": [
        {
          "workflow": "create_version"
        },
        {
          "workflow": "update_metadata"
        },
        {
          "workflow": "upload_screenshots"
        },
        {
          "workflow": "submit_for_review"
        }
      ]
    },
    "create_version": {
      "private": true,
      "description": "Create App Store version",
      "steps": [
        {
          "name": "create_version",
          "run": "asc versions create --app $APP_ID --version $VERSION --platform $PLATFORM --output json",
          "outputs": {
            "VERSION_ID": "$.id"
          }
        }
      ]
    },
    "update_metadata": {
      "private": true,
      "description": "Update app metadata",
      "steps": [
        {
          "name": "update_en_US",
          "run": "asc localizations update --version ${steps.create_version.VERSION_ID} --locale en-US --description \"$(cat metadata/en-US/description.txt)\" --keywords \"$(cat metadata/en-US/keywords.txt)\" --whats-new \"$(cat metadata/en-US/whats-new.txt)\""
        },
        {
          "name": "update_es_ES",
          "run": "asc localizations update --version ${steps.create_version.VERSION_ID} --locale es-ES --description \"$(cat metadata/es-ES/description.txt)\" --keywords \"$(cat metadata/es-ES/keywords.txt)\" --whats-new \"$(cat metadata/es-ES/whats-new.txt)\""
        }
      ]
    },
    "upload_screenshots": {
      "private": true,
      "description": "Upload screenshots",
      "steps": [
        {
          "name": "upload_iphone",
          "run": "asc screenshots upload --app $APP_ID --version-id ${steps.create_version.VERSION_ID} --path screenshots --device-type IPHONE_65"
        },
        {
          "name": "upload_ipad",
          "run": "asc screenshots upload --app $APP_ID --version-id ${steps.create_version.VERSION_ID} --path screenshots --device-type IPAD_PRO_3GEN_129"
        }
      ]
    },
    "submit_for_review": {
      "private": true,
      "description": "Run the App Store release pipeline",
      "steps": [
        {
          "name": "ensure_ipa",
          "run": "test -f \"$IPA_PATH\""
        },
        {
          "name": "publish_appstore",
          "if": "SUBMIT",
          "run": "asc publish appstore --app $APP_ID --ipa $IPA_PATH --version $VERSION --submit --confirm"
        }
      ]
    }
  }
}
```

Run with:

```bash  theme={null}
asc workflow run release SUBMIT:true VERSION:2.0.0
```

`create_version` declares `VERSION_ID` once, and every later sub-workflow reads
it as `${steps.create_version.VERSION_ID}`. Step names that declare `outputs`
must stay unique across workflows that can run together, which is why the
producer is named once and referenced everywhere else.

## CI/CD Integration

### GitHub Actions

```yaml  theme={null}
name: Release Workflow

on:
  workflow_dispatch:
    inputs:
      version:
        description: 'Version number (e.g., 1.0.0)'
        required: true

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Install asc CLI
        run: |
          curl -fsSL https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/install.sh | bash
      
      - name: Configure credentials
        env:
          ASC_KEY_ID: ${{ secrets.ASC_KEY_ID }}
          ASC_ISSUER_ID: ${{ secrets.ASC_ISSUER_ID }}
          ASC_PRIVATE_KEY: ${{ secrets.ASC_PRIVATE_KEY }}
          ASC_APP_ID: ${{ secrets.ASC_APP_ID }}
        run: |
          echo "Credentials configured"
      
      - name: Run release workflow
        env:
          VERSION: ${{ github.event.inputs.version }}
        run: |
          asc workflow run release "VERSION:$VERSION"
      
      - name: Upload workflow output
        uses: actions/upload-artifact@v3
        with:
          name: workflow-output
          path: /tmp/workflow-*.log
```

### GitLab CI

```yaml  theme={null}
stages:
  - release

release:production:
  stage: release
  tags:
    - linux
  script:
    - curl -fsSL https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/install.sh | bash
    - asc workflow run release VERSION:$VERSION
  variables:
    VERSION: "1.0.0"
  only:
    - tags
  when: manual
```

## Advanced Features

### Dry Run Mode

Preview workflow execution without running commands:

```bash  theme={null}
asc workflow run beta --dry-run
```

Shows:

* Steps that would be executed
* Environment variables
* Command interpolation
* Workflow order

### Private Workflows

Mark workflows as private (only callable from other workflows):

```json  theme={null}
{
  "workflows": {
    "helper": {
      "private": true,
      "description": "Helper workflow - not directly callable",
      "steps": [
        {"name": "help", "run": "echo Helping..."}
      ]
    },
    "main": {
      "description": "Main workflow that calls helper",
      "steps": [
        {"workflow": "helper"}
      ]
    }
  }
}
```

```bash  theme={null}
# Works
asc workflow run main

# Fails - private workflow
asc workflow run helper
```

List including private workflows:

```bash  theme={null}
asc workflow list --all
```

### Custom Workflow File

Use a different workflow file:

```bash  theme={null}
asc workflow run beta --file ./custom-workflows.json
```

### Pretty JSON Output

```bash  theme={null}
asc workflow run beta --pretty
```

## Best Practices

1. **Use descriptive names**: Name workflows and steps clearly

2. **Add descriptions**: Document what each workflow does

3. **Validate before running**: Always run `asc workflow validate` after editing

4. **Use environment variables**: Parameterize workflows for reusability

5. **Handle errors**: Define `error` hooks to clean up on failure

6. **Test with dry-run**: Use `--dry-run` to preview execution

7. **Keep workflows focused**: Break complex workflows into composable sub-workflows

8. **Version control workflows**: Store `.asc/workflow.json` in git

9. **Document required parameters**: Note required `KEY:VALUE` parameters in descriptions

10. **Use private workflows**: Extract common logic into private sub-workflows

## Security Considerations

<Warning>
  * Only run workflows from trusted sources
  * Review workflow files before execution
  * Avoid hardcoding secrets—use environment variables
  * In CI/CD, use encrypted secrets for credentials
  * Don't run untrusted workflows on PRs with access to secrets
  * Set `ASC_READ_ONLY=1` for audit, reporting, and agent sessions that must never write
</Warning>

### Read-only runs

Export `ASC_READ_ONLY=1` (or pass the global `--read-only` flag) when a workflow, CI job, or agent session is only allowed to inspect App Store Connect. Every command still runs, but any `POST`, `PATCH`, `PUT`, or `DELETE` is refused before it leaves the process with exit code `6`. This is enforced in the HTTP clients, not per command, so it holds for every command in the workflow, and workflow steps inherit the mode as `ASC_READ_ONLY=1` so a nested `asc` call is refused too. Steps that call other tools are outside the guarantee. See [Read-only mode](/concepts/read-only-mode).

```bash  theme={null}
ASC_READ_ONLY=1 asc workflow run audit
```

### Safe Practices

```json  theme={null}
// Good - uses environment variable
"run": "asc builds list --app $APP_ID"

// Bad - hardcoded sensitive data
"run": "asc builds list --app 123456789"

// Good - credentials from environment
"env": {
  "ASC_KEY_ID": "$CI_ASC_KEY_ID"
}

// Bad - credentials in workflow file
"env": {
  "ASC_KEY_ID": "ABC123XYZ"
}
```

## Troubleshooting

### Validation Errors

**Problem**: `asc workflow validate` reports errors.

**Solution**: Check for:

* Circular workflow dependencies
* Missing workflow definitions
* Invalid JSON syntax
* Unknown step types

### "Workflow not found"

**Problem**: Workflow name doesn't exist in file.

**Solution**: List available workflows:

```bash  theme={null}
asc workflow list
```

### Variable Not Interpolated

**Problem**: `$VARIABLE` appears literally in output.

**Solution**: Ensure the variable is:

* Defined in `env` (global or workflow)
* Passed as runtime parameter: `VARIABLE:value`
* Available in system environment

### Step Fails Silently

**Problem**: Step executes but produces no output.

**Solution**:

* Check step output is written to stderr (workflow stdout is JSON-only)
* Enable verbose mode (if available)
* Add explicit `echo` statements

### Workflow Hangs

**Problem**: Workflow stops and doesn't complete.

**Solution**:

* Check for interactive commands (not supported)
* Verify commands don't wait for user input
* Add timeout to long-running commands
