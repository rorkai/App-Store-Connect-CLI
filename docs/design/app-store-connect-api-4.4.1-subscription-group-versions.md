# App Store Connect API 4.4.1 subscription group versions

## Placement and command shape

Subscription group versions extend the existing `asc subscriptions groups`
taxonomy:

```text
asc subscriptions groups versions create --group-id "GROUP_ID"
asc subscriptions groups versions list --group-id "GROUP_ID"
asc subscriptions groups versions view --version-id "VERSION_ID"
asc subscriptions groups versions localizations list --version-id "VERSION_ID"
asc subscriptions groups versions localizations create --version-id "VERSION_ID" --locale "en-US" --name "Premium"
asc subscriptions groups versions localizations view --id "LOCALIZATION_ID"
asc subscriptions groups versions localizations update --id "LOCALIZATION_ID" --name "Premium Plus"
asc subscriptions groups versions localizations delete --id "LOCALIZATION_ID" --confirm
asc subscriptions groups versions links versions --group-id "GROUP_ID"
asc subscriptions groups versions links localizations --version-id "VERSION_ID"
```

The current stable `asc subscriptions groups localizations ...` commands keep
using the v1 group-scoped endpoints. No existing command, flag, payload, output,
or exit code is removed or redirected.

The existing group list and view commands gain sparse-field and include controls
needed to retrieve versions: `--include`, `--fields`, `--version-fields`, and
`--versions-limit`. Existing invocations keep their current request shape.

## OpenAPI contract

The implementation covers exactly these newly added 4.4.1 operations:

| Method | Path | Request / response |
| --- | --- | --- |
| `POST` | `/v1/subscriptionGroupVersions` | `SubscriptionGroupVersionCreateRequest` / `SubscriptionGroupVersionResponse` |
| `GET` | `/v1/subscriptionGroupVersions/{id}` | `SubscriptionGroupVersionResponse` |
| `GET` | `/v1/subscriptionGroups/{id}/versions` | `SubscriptionGroupVersionsResponse` |
| `GET` | `/v1/subscriptionGroups/{id}/relationships/versions` | `SubscriptionGroupVersionsLinkagesResponse` |
| `GET` | `/v1/subscriptionGroupVersions/{id}/localizations` | `SubscriptionGroupLocalizationsV2Response` |
| `GET` | `/v1/subscriptionGroupVersions/{id}/relationships/localizations` | `SubscriptionGroupVersionLocalizationsLinkagesResponse` |
| `POST` | `/v2/subscriptionGroupLocalizations` | `SubscriptionGroupLocalizationV2CreateRequest` / `SubscriptionGroupLocalizationV2Response` |
| `GET` | `/v2/subscriptionGroupLocalizations/{id}` | `SubscriptionGroupLocalizationV2Response` |
| `PATCH` | `/v2/subscriptionGroupLocalizations/{id}` | `SubscriptionGroupLocalizationV2UpdateRequest` / `SubscriptionGroupLocalizationV2Response` |
| `DELETE` | `/v2/subscriptionGroupLocalizations/{id}` | no response body |

Creating a version requires only a `subscriptionGroup` relationship. Creating
a v2 localization requires `name`, `locale`, and a `version` relationship whose
resource type is `subscriptionGroupVersions`; `customAppName` is optional and
nullable. Updating a v2 localization accepts nullable `name` and
`customAppName`. Explicit `--clear-name` and `--clear-custom-app-name` flags map
to JSON `null`; omitted flags are omitted from the payload.

Version list supports `filter[state]`, sparse fields, includes, `limit`,
`limit[localizations]`, `links.next`, and CLI aggregation with `--paginate`.
Version-localization list supports its endpoint-specific fields, `include=version`,
`limit`, `links.next`, and `--paginate`. Relationship commands return raw
resource linkages and support the endpoint `limit`, `links.next`, and
`--paginate` controls.

The modified group list and detail operations support the new
`include=versions`, `fields[subscriptionGroupVersions]`, the `versions` group
sparse field, and `limit[versions]` values. This change does not alter the
default query generated by either operation.

Because `SubscriptionGroup` is a shared schema, the typed `versions`
relationship is also preserved when a group is returned by legacy group create
or update calls, included by a v1 group-localization response, or included by an
app response. Structured decode tests cover all five shapes: direct group,
group create, group update, localization included data, and app included data.
The v2 localization sparse-field allowlist intentionally excludes `state`:
4.4.1 defines that attribute only on the legacy v1 localization schema.

## Behavior and failures

All successful commands write the selected table, JSON, Markdown, or XML data
to stdout. Validation and API diagnostics use stderr. Missing required flags,
invalid state/include selections, invalid limits, conflicting set/clear flags,
and update requests without changes exit with usage status 2 before auth or
network access. Delete requires `--confirm` and never prompts interactively.

Every outbound App Store Connect call uses `shared.ContextWithTimeout`.
Pagination validates `links.next` URLs with the shared ASC URL policy.

## Alternatives considered

Reusing `asc subscriptions groups localizations` with a version flag would make
the same command silently select either v1 or v2 and would complicate required
relationship validation. A dedicated `versions localizations` subtree makes the
API generation and owning relationship explicit.

A new top-level `subscription-group-versions` command would mirror the raw API
resource, but it would split closely related group workflows across top-level
taxonomies. Nesting versions under the existing group command keeps discovery
and compatibility clearer.

Review submission item plumbing is intentionally outside this PR. It is a
cross-cutting request contract shared with IAP and subscription versions and is
owned by the separate review integration change.
